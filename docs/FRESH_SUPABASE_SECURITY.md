# Fresh Supabase security and bootstrap notes

The migration chain intentionally creates no default administrator. Before admin login can work, an operator must create the first `admin_users` row out of band after applying the schema. Generate a unique random salt and a 64-byte scrypt digest in a trusted local environment; store `password_hash` in the format `scrypt$<salt>$<hex-digest>`. Insert that value through the Supabase SQL editor or another trusted administrative connection, and never put the password or digest in source control. Do not create an account through browser-side admin management.

The review sign-in API verifies that scrypt format on the server and checks TOTP there. Admin reset codes and the old direct browser admin-user maintenance flows have not been moved to protected server APIs. Do not use those flows; password reset and admin account management need server routes before production use. Several other legacy dashboard, CRM, engineer, employee, customer, notification, and ticket-reading operations still call Supabase directly from the browser. Migration 00041 removes their anonymous/authenticated table privileges, so those operations will fail until moved behind server routes that verify the signed admin/employee session. The Support page's legacy customer lookup also needs a server route before ticket submission will work. This is intentional to avoid treating localStorage as authorization.

Public operations left available through the database are limited to submitting support tickets, contact forms, chatbot feedback/ratings/escalations, reading public reference data (AMC plans, exchange rates, active offices, published knowledge-base articles), incrementing published-article metrics, generating ticket IDs, and fetching one chatbot escalation by its unguessable session token. Chat transcript persistence uses a server API keyed by the browser's random session token. The chatbot escalation RPC and public insert endpoints should be reviewed alongside deployment configuration and abuse controls.

The `uploads` Storage bucket remains public for repair-photo uploads. Review the bucket's public-read behavior and upload abuse controls before production use. The review API stores submissions as `PENDING`, returns only approved whitelisted fields publicly, and keeps review management behind the signed admin cookie and service-role server client.

Known missing or unverified Edge Functions remain: `archive-logs`, `create-stripe-payment-intent`, and `send-reset-code`. Existing folder findings remain: `generate-scheduled-reports` is the renamed folder for the earlier scheduled-report function, and `monitor-slas` is the corrected name for the earlier `monitore-slas` folder. These edits do not establish that any function is deployed.
